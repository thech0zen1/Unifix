- Track every meaningful status change.
- Escalate neglected tickets automatically.
- Maintain complete historical records.
- Enforce campus-level data isolation.
- Provide authorized global oversight.
- Use AI to extract structured information and identify patterns.
- Remain functional when AI services are unavailable.
- Keep the system modular enough to extend over time.

# 7. CAMPUS REGISTRY AND IDENTITY VERIFICATION

The system must support multiple campuses, each with its own authorized users and operational data.

Create a proper campus registry in PostgreSQL.

A campus should have fields such as:

- UUID.
- Name.
- Unique campus code.
- Location or region.
- Time zone.
- Active/inactive status.
- Created and updated timestamps.

Do not hard-code the campus list into frontend source code.

## Authorized identity registry

Create a normalized database structure for campus-authorized identities.

For example, Campus A may contain authorized identities for several students, teachers, administrators, and maintenance workers.

An authorized identity may contain:

- Campus ID.
- Normalized email address, if available.
- Normalized phone number, if available.
- Display name.
- Optional external student or employee identifier.
- Expected membership role.
- Active/inactive status.
- Verification or provisioning metadata.
- Creation and update timestamps.

Use appropriate unique constraints and indexes.

Avoid duplicating the same identity information across unrelated records.

An authorized identity is a registry entry used to determine eligibility. It is not itself proof that a person controls the associated email address or phone number.

## Verification workflow

The initial onboarding flow should:

1. Allow the user to select a campus.
2. Accept an authorized email address or phone number.
3. Normalize the supplied identifier.
4. Check the campus's authorized identity registry.
5. Reject unknown or inactive identities.
6. Continue through the configured OTP simulation.
7. Establish the authenticated account and campus membership.
8. Issue authentication credentials only after successful verification.

The backend must perform these checks.

Do not trust a client-supplied campus ID, role, name, or verification flag.

## Seed data

Create fictional seed data for development.

Include multiple campuses and several authorized identities per campus.

Never invent real people's personal information for production use.

Seed data must be clearly identified as development data and must not accidentally become a production account registry.

# 8. AUTHENTICATION AND SESSION SECURITY

The initial implementation must work without a paid email or SMS provider.

## Simulated OTP

Build a development OTP provider that supports the onboarding flow without sending actual email or SMS messages.

The design must allow replacing the simulated provider with a real provider later.

The interface should resemble a real verification flow, but must not falsely claim that a real message has been sent.

Implement safe development behavior:

- Simulated OTP delivery or clearly documented development display.
- Expiration.
- Verification-attempt limits.
- Resend cooldown.
- Rate limiting.
- Account and identifier checks.
- Protection against brute-force attempts.
- Clear separation between development and production modes.

Never silently enable a predictable development OTP in production.

Do not commit real secrets.

## Authentication tokens

Use a secure session architecture appropriate for a mobile application and web dashboard.

Implement:

- Short-lived access tokens.
- Refresh-token rotation.
- Refresh-token revocation.
- Server-side session tracking.
- Logout.
- Logout-all-sessions where appropriate.
- Expiration checks.
- Revocation after suspicious or invalid refresh behavior.
- Secure storage on mobile.
- Appropriate browser cookie and CSRF protections if refresh credentials are stored in cookies.

If refresh tokens are opaque rather than JWTs, that is acceptable and may be preferable. Store only a secure hash of the refresh token or equivalent secret material in the database where applicable.

Do not store long-lived authentication secrets in ordinary browser local storage.

# 10. TICKET REPORTING WORKFLOW

Reporting must be simple enough for a nontechnical user.

Support two reporting modes.

## Mode A: Manual reporting

A user should be able to create a ticket without interacting with AI.

The manual flow should collect the information required by the selected ticket type, including as appropriate:

- Short title.
- Description.
- Campus.
- Location.
- Category.
- Severity.
- Impact.
- Urgency.
- Optional attachments.
- Anonymous reporting preference.

Avoid requiring every field if the information is not necessary to submit an initial report.

The backend must validate and normalize the submission.

## Mode B: AI-assisted reporting

A user describes the problem in natural language.

Example:

"The lights in the second-floor corridor of the library have not worked since yesterday."

The mobile application sends the text to the Express backend.

The backend sends the appropriate request to the configured LLM provider.

The AI may:

- Extract a suggested title.
- Summarize the issue.
- Suggest a category.
- Extract the reported location.
- Suggest severity.
- Suggest impact.
- Suggest urgency.
- Identify missing information.
- Ask relevant follow-up questions.
- Identify uncertainty.
- Suggest potentially related existing tickets.

The AI must not invent facts.

If the location is unclear, ask the user.

If severity is unclear, request clarification or use a conservative, explicitly marked suggestion.

Distinguish extracted facts from inferred recommendations.

## Confirmation before submission

The AI must never submit a ticket automatically.

The workflow must be:

1. User describes the issue.
2. Backend requests structured AI analysis.
3. AI returns proposed fields and missing-information questions.
4. User answers follow-up questions as needed.
5. User reviews and edits the proposed ticket.
6. Backend validates the final fields.
7. User explicitly confirms submission.
8. Backend creates the ticket and initial history transactionally.
9. The application displays the ticket ID and status.

Manual reporting must always remain available.

## Structured AI output

Use a versioned, validated response schema.

Prefer structured JSON output supported by the configured provider.

Validate all AI responses with Zod or an equivalent strict schema.

Handle:

- Missing fields.
- Unexpected fields.
- Invalid enum values.
- Malformed JSON.
- Refusals.
- Timeouts.
- Empty responses.
- Unsupported model capabilities.

AI output is untrusted input. Never execute arbitrary code, SQL, shell commands, or database instructions generated by the model.

# 11. DUPLICATE AND SIMILARITY DETECTION

Before a user submits a new report, the backend may request an AI-assisted similarity analysis.

The system should retrieve an appropriately scoped set of candidate tickets and provide only the context necessary for comparison.

Consider:

- Similar descriptions.
- Same or nearby location.
- Same category.
- Similar symptoms.
- Current ticket status.
- Whether the earlier issue is already resolved.
- Recency.
- Relevant campus boundaries.

Do not compare or disclose tickets from unauthorized campuses.

The AI should return ranked suggestions with explanations and uncertainty.

For example:

"This may be the same lighting problem already reported in the second-floor library corridor."

The user must decide what to do.

Possible actions:

- Continue creating a new ticket.
- Open the suggested existing ticket.
- Select "I have this issue too."

## Endorsements

Selecting "I have this issue too" must create an endorsement or affected-user association with the existing ticket.

Enforce uniqueness for a user-ticket pair.

For example:

`UNIQUE(ticket_id, user_id)`

A repeated request must not inflate endorsement counts.

Define whether the original reporter counts as one affected person and how endorsement totals are displayed. Keep affected-user counts consistent and transactionally safe.

Do not automatically merge reports based solely on AI similarity.

## Management duplicate handling

Authorized management may mark a ticket as a genuine duplicate.

Record:

- Duplicate ticket ID.
- Canonical ticket ID.
- Acting manager.
- Timestamp.
- Optional reason.
- Any permitted changes to assignments or notifications.

Preserve the duplicate ticket and its history.

A duplicate should not vanish from the historical record.

# 13. TICKET LIFECYCLE AND THREE-WEEK ESCALATION

This is a core feature. Implement it as a first-class backend workflow, not a frontend timer.

## 13.1 Required behavior

The escalation clock begins when a ticket is created.

If the ticket's current progress stage remains unchanged for 21 days, the system must issue a management alert.

The same rule applies to subsequent stages.

Example:

1. A ticket is created as `OPEN`.
2. It remains `OPEN` for 21 days.
3. The system alerts management that the ticket has not been acknowledged or progressed.
4. A manager acknowledges it, changing the status to `ACKNOWLEDGED`.
5. The stage timer restarts.
6. If it remains `ACKNOWLEDGED` for another 21 days, the system sends another management warning.
7. The manager assigns it or changes it to `IN_PROGRESS`.
8. A new stage timer begins.
9. If the ticket remains in that stage without meaningful progress for 21 days, the system sends another escalation.
10. The same principle continues until the issue is resolved, closed, rejected through a valid workflow, or otherwise reaches a documented terminal state.

Do not treat a status update as proof that meaningful work occurred.

A manager must not be able to bypass escalation indefinitely by repeatedly changing a status without documenting actual progress.

## 13.2 Define meaningful progress

Implement a structured progress event or equivalent model.

Meaningful progress may include:

- Acknowledgement by responsible management.
- Assignment to a responsible department or person.
- A documented investigation update.
- A documented maintenance action.
- A change in operational state.
- A justified transition to waiting, including the reason and expected next action.
- A documented resolution attempt.

A generic comment such as "still checking" must not automatically reset every escalation clock forever.

Define which events restart a stage timer and which merely add information to the ticket history.

Record the event type, actor, timestamp, and relevant details.

## 13.3 Stage-specific escalation

Maintain explicit escalation rules.

At minimum:

- Ticket creation starts the first timer.
- Every meaningful status-stage transition starts the next stage timer.
- If a stage remains unchanged for 21 days, alert management.
- After an escalation, further escalation behavior must be explicit and configurable.
- Meaningful progress must update the appropriate timer according to the rules.
- Resolved, closed, and other terminal states must not continue generating ordinary overdue alerts.
- Reopening must reactivate the appropriate workflow and timer.

Do not accidentally reset the timer when editing an unrelated ticket field.

Do not reset it because of an automated background update.

## 13.4 Critical issues

Critical issues must have shorter escalation periods than ordinary issues.

Implement a configurable escalation policy based on severity or official priority.

Do not hard-code a collection of unexplained numbers throughout the codebase.

Use centralized configuration or database-backed policy records.

Choose sensible initial defaults, document them, and make them configurable by authorized administrators.

If an issue involves immediate danger, show appropriate safety guidance and make the urgent reporting route clear. The platform must not represent an AI-generated severity estimate as a verified safety assessment.

## 13.5 Notifications

Escalations must notify management.

When a ticket has not been resolved or has failed to progress according to the escalation policy, also notify the original reporter as specified by the applicable policy.

For anonymous reports, the notification must not disclose the reporter's identity to ordinary users.

Notifications should identify:

- Ticket ID.
- Current status.
- Time spent in the current stage.
- Reason for escalation.
- Last meaningful progress event.
- Responsible department or assignee, if known.
- Required management action.

Implement an in-app notification system initially.

Design the notification layer so email, push notifications, or other channels can be added later without rewriting ticket business logic.

Do not pretend an external notification has been delivered if no provider is configured.

## 13.6 Reliable background processing

The escalation system must run independently of whether a user has the app open.

Implement a reliable scheduled background process suitable for the initial architecture.

It may use a scheduler within the backend deployment, provided the deployment is designed to keep that scheduler running. If the deployment model cannot guarantee that, document and implement an appropriate separate scheduling mechanism.

Use database-backed processing, idempotency, or equivalent safeguards so that:

- The same escalation is not repeatedly created on every scheduler run.
- Multiple scheduler executions do not produce duplicate notifications.
- A crash does not silently lose overdue tickets.
- Retrying a failed operation is safe.
- Escalation history remains auditable.

Do not add Redis or a distributed job system without demonstrating why the simpler approach is insufficient.

## 13.7 Resolved and historical tickets

When an issue is resolved:

- Record the resolution timestamp.
- Record the resolution summary.
- Record who resolved it.
- Preserve all earlier history.
- Remove it from the active-work queue.
- Keep it searchable in historical records.
- Keep it available for authorized analytics.
- Stop ordinary stage-escalation alerts.

When a resolved issue is reopened:

- Record the actor and reason.
- Preserve the previous resolution.
- Create a new history event.
- Return it to the active workflow.
- Restart the appropriate escalation clock.
- Notify relevant users and management according to policy.

"Cleared" means removed from the active queue, not deleted from the database.

Resolved, closed, rejected, and duplicate tickets must remain available in authorized historical views.

## 13.8 Reporter reopening

The original reporter must be able to request reopening when an issue was marked resolved but the problem remains unsolved.

Implement a controlled workflow:

- The reporter can submit a reopen request with a reason.
- The system records the request.
- The ticket can be reopened according to the configured policy.
- Management receives a notification.
- The original history remains intact.

If the policy allows immediate reporter-initiated reopening, record the action and notify management. If the policy requires review, display the request as pending.

Choose and document a coherent initial policy. Do not silently discard reopening requests.

# 31. NON-NEGOTIABLE PRODUCT RULES

The following requirements must remain true throughout development.

1. There is one shared backend for the mobile and web applications.
2. Campus data must be isolated through backend authorization.
3. There are three broad access layers: ordinary users, campus management, and supermanagement.

5. Authorized campus management and supermanagement can see the identity and phone number of anonymous reporters.
6. AI must never submit a ticket without explicit user confirmation.
7. AI must never automatically merge potentially duplicate tickets.
8. Manual reporting must remain available without AI.
9. AI failure must not disable core ticket management.
10. The escalation clock starts when a ticket is created.
11. A ticket that remains unchanged at a progress stage for 21 days must trigger the configured management escalation.
12. The same stage-based principle applies to subsequent stages.
13. Critical issues must support shorter escalation periods.
14. Meaningful progress must be distinguished from superficial status changes.
15. Escalations and notifications must be idempotent and auditable.
16. Resolved and closed tickets must remain available in historical records.
17. Resolution removes a ticket from active work; it does not delete the record.
18. Reopening must preserve the original history.
19. Official management priority must be distinguishable from AI-suggested priority.
20. AI insights must distinguish factual metrics from recommendations.
21. Secrets must not be committed to Git or exposed to clients.
22. The mobile app must not contain privileged backend credentials.
23. The project must remain modular and recoverable across agent sessions.
24. The development agent must not falsely claim that incomplete or unverified work is complete.
